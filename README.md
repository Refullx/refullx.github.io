## 三、几个基础命令是什么意思

刚接触命令行时这几个最容易混，记一下：

| 命令 | 全称/含义 | 干什么用的 |
| --- | --- | --- |
| `pwd` | print working directory | 告诉你"我现在在哪个文件夹里" |
| `ls` | list | 列出当前文件夹里有哪些文件（`ls -a` 能看到隐藏文件） |
| `cd 目录名` | change directory | 进入某个文件夹，`cd ..` 是退回上一级 |
| `mkdir 目录名` | make directory | 新建一个文件夹，`mkdir -p a/b/c` 可以一次建多层 |
| `touch 文件名` | — | 建一个空文件 |
| `rm 文件名` | remove | 删文件（删文件夹要加 `-r`，这个命令要小心，没有回收站） |

最常用的其实是 `cd` 和 `ls`：走到哪先看一眼自己在哪，再看一眼这里有啥，就不容易搞错。

## 四、Git 是怎么用的

### 4.1 最核心的三步

```bash
git add .                       # 把改动放进"暂存区"，相当于打包准备发出去
git commit -m "说明这次改了啥"    # 打一个快照，存到本机仓库里
git push                        # 把本机的快照推到 GitHub 上，别人就能看到了
```

`add` 是"挑哪些文件要提交"，`commit` 是"给这次改动拍张照并写个说明"，`push` 是"把照片上传"。这三次动作是分开的，好处是可以挑一部分文件先提交，不用一股脑全丢进去。

### 4.2 为什么要分支

假设你想加一个新功能，但不确定能不能做成。直接在主分支上改，改崩了整个项目就废了。所以开一条分支：

```bash
git checkout -b feature-xxx     # 新建并切换到 feature-xxx 分支
# ... 随便改，改崩了也不影响 main ...
git checkout main               # 切回主分支
git merge feature-xxx           # 确认没问题了，把 feature-xxx 合并进来
git branch -d feature-xxx       # 删掉用完的分支，保持干净
```

分支可以理解成"平行世界"：你在另一条时间线上随便折腾，主线的代码始终是能跑的版本。折腾成功了再**合并**回主线，失败了删掉分支就行，主线一点没动。

如果两个分支改了同一个文件的同一行，`merge` 会**冲突**，Git 不知道该留谁的，就会停下来让你手工选。解冲突就是打开那个文件，找到 `<<<<<<<` 和 `>>>>>>>` 之间的两段代码，删掉不要的那段和那些标记符号，然后重新 `add` + `commit`。

### 4.3 查看历史

```bash
git log --oneline               # 一行一条，看提交历史
git status                      # 看当前哪些文件改了、还没提交
git diff                        # 看具体改了哪些内容
```

`git status` 是最该养成习惯用的，搞不清楚自己改动状态的时候，敲一下它基本就有答案了。

## 五、为什么选 MIT 协议

挑开源协议主要看一个问题：**别人能怎么用你的代码**。

| 协议 | 核心要求 | 适合谁 |
| --- | --- | --- |
| MIT | 只要保留版权声明，随便用，可以闭源商用 | 想让最多的人无障碍使用 |
| Apache 2.0 | 多一条专利授权，修改要说明 | 公司级项目，在意专利风险 |
| GPL | 用了我的代码，你的项目也必须开源 | 想强制开源、防止被闭源商用 |

我选 **MIT**，理由很直接：

1. **要求最少**——别人只要保留一行版权声明，其他爱干嘛干嘛，包括拿去做商业闭源项目。作业的目的是让人看、让人跑起来，MIT 的门槛最低。
2. **兼容性最好**——MIT 的代码可以被 GPL 项目吸收；反过来 GPL 的代码 MIT 项目不能碰。选 MIT 等于默认兼容所有人。
3. **短**——全文不到 20 行，普通人真看得完。Apache 2.0 那种法律文件长度，说实话没人会读。

代价是：如果我开源了某个特别有价值的东西，别人拿去闭源赚钱我也管不着。对一个大一作业来说，这个代价可以忽略。
